Статический сайт-витрина, который показывает, **как выглядят дашборды регламента управления производственной IT-системой (Production IT System Governance)** на синтетических данных. Открывается в браузере без сборки и бэкенда, деплоится на GitHub Pages / Netlify за минуты.

> **Данные сгенерированы для демонстрации. Не использовать для реальных решений.**
> Все записи синтетические: вымышленные команды, модули и ID. Нет PII, реальных брендов и отзывов.

## Зачем это

Проект — визуальное приложение к [Паспорту проекта](Pasport_Proekta_Reglament_Upravlenia_Prod_IT_System.docx) и [презентации](presentation.pptx). В паспорте сформулированы три опоры регламента: прослеживаемость по ГОСТ Р ИСО 9000/9001, Канбан-метод для управления потоком и анализ поля сил К. Левина. Витрина показывает, **как эти идеи выглядят на экране**: CFD, WIP/бэклог, поток «поступило − закрыто», возраст незавершённых задач и Lead Time в перцентилях — по тем же строкам трекера, что в таблице.

## Пресет модели: `dev.md`

Файл `dev.md` — системный пресет для AI-модели, задающий роль и границы работы над витриной. Он описывает:

- **Роль.** Senior-эксперт по аналитике, дизайну дашбордов и frontend-прототипированию, создающий витрины на синтетических данных.
- **Цель.** Генерировать полностью рабочий статический сайт с дашбордами: фильтры, графики, KPI, таблица и выводы — всё открывается в браузере без сборки.
- **Жёсткие ограничения.** Только синтетика (без PII и реальных брендов), воспроизводимость по seed, отсутствие бэкенда, дисклеймер «Данные сгенерированы для демонстрации» на каждом экране, доступность, отказ от chart junk.
- **Архитектура по умолчанию.** Gallery → страница дашборда → Data & Methodology.
- **Технологический дефолт.** HTML/CSS/JS без сборки, ECharts через CDN, inline-SVG иконки, светлая нейтральная палитра, деплой на GitHub Pages / Netlify.
- **Формат ответа.** Бриф → структура файлов → полный код каждого файла → инструкция запуска → чек-лист качества.

Пресет гарантирует, что каждый сгенерированный проект соответствует проектному регламенту и не выдаёт синтетические данные за реальные.

## Быстрый старт

Сайт — набор статических файлов. Никакой сборки, никаких зависимостей, кроме CDN для графиков.

### Локально

1. Скачайте папку проекта целиком.
2. Откройте `index.html` в браузере (двойной клик или `file://…/index.html`).
3. На вкладке **1. Данные задач** выберите `samples/tasks-schema.json`, затем `samples/tasks.csv`. Либо нажмите **«Скачать CSV»** по seed — витрина сгенерирует данные сама.
4. Перейдите на вкладку **2. Состояние системы** — графики и KPI пересчитаются.

> Первый запуск без файлов показывает пустые состояния — это нормально, у витрины нет встроенного демо-набора «из коробки», только генератор по seed.

### Деплой

**GitHub Pages**

1. Запушьте репозиторий на GitHub.
2. Settings → Pages → Source: `Deploy from a branch`, ветка `main`, папка `/` (root).
3. Через минуту сайт доступен по `https://<user>.github.io/<repo>/`.

**Netlify**

1. New site from Git → выберите репозиторий.
2. Build command: пусто. Publish directory: `.` (корень).
3. Deploy.

Никаких секретов и переменных окружения — бэкенда нет.

## Как устроены данные

### Синтетический генератор (`assets/data.js`)

- **Детерминизм.** Все данные генерируются по seed (mulberry32). Одинаковый seed → одинаковый набор. Seed вводится на вкладке 1 в поле «Демо-набор по seed».
- **Дата среза зафиксирована:** `29.10.2026`. Окно — 26 недель. Разогрев 90 дней: попадают задачи, открытые раньше окна, но не закрытые к его началу.
- **Структура, а не шум:** тренд + 28-дневная сезонность + логнормальные длительности + сегменты (команда, тип работы, класс обслуживания).
- **Аномалия заложена намеренно:** последние 60 дней тестирование замедляется до ×2,2 — узкое место видно на вкладке 2.

### Схема CSV (`samples/tasks-schema.json`)

Схема задаёт всё: разделитель, кодировку, колонки, типы, форматы дат, маппинг. Ключевые для вкладки 2 блоки:

```jsonc
"mapping": {
  "id": "id",
  "title": "title",
  "search": ["id", "title"],
  "segments": ["team", "type", "service_class"],
  "workflow": { "stages": ["open", "analysis", "dev", "test", "release"], "doneStage": "closed" },
  "charts": {
    "cfd": {
      "stages": ["open", "analysis", "dev", "test", "release", "closed"]
    },
    "leadTime": { "startDate": "open" },
    "forecast": { "backlogStages": ["open"] }
  }
}
```

- `cfd.stages` — порядок этапов; последний ключ считается «закрытой» задачей.
- `leadTime.startDate` — от какой колонки считать возраст и Lead Time (по умолчанию — первый этап).
- `forecast.backlogStages` — какие этапы относятся к бэклогу (по умолчанию — первый этап).

Если чего-то нет — вкладка 2 покажет подсказку «добавьте `mapping.charts.cfd`» и не упадёт.

### Свои данные

1. Опишите формат выгрузки в JSON по образцу `samples/tasks-schema.json`.
2. На вкладке 1 нажмите **«Выбрать JSON-файл»** — схема валидируется, ошибки показываются с путём к полю.
3. Нажмите **«Загрузить данные из CSV»**. Строки с ошибками пропускаются с указанием номера и причины (или загрузка отменяется, если в схеме `"onRowError": "fail"`).
4. Данные один раз грузятся в память браузера и доступны на всех вкладках до перезагрузки.

Файлы не уходят на сервер — обрабатываются локально.

## Методология вкладки «Состояние системы»

Все расчёты — по тем же строкам, что и таблица, с учётом фильтров поиска и сегментов.

| Показатель | Формула | Источник |
|---|---|---|
| В системе | `N(открыта) − N(закрыта)` на дату среза | Паспорт §5.3 |
| Бэклог | `N(открыта) − N(первый этап после бэклога)` | §3.2 канбан-поток |
| WIP | `N(первый этап после бэклога) − N(закрыта)` | §3.2 |
| Узкое место | Этап WIP с максимальным ростом очереди за 28 дней | §5.1, поле Левина |
| Баланс потока, 28 дн. | Поступило − закрыто | §5.1 Throughput |
| P50 / P85 Lead Time | Nearest-rank по задачам, закрытым за 26 недель (≥ 5 задач) | §5.1, §7 «перцентили, а не среднее» |
| Возраст задачи | Рабочие дни от `leadTime.startDate` до среза | §5.1 WIP Age |
| Старение | Незавершённые задачи старше P85 | §5.1 порог-реакция |
| Закон Литтла | Среднее время ≈ WIP ÷ пропускная способность за 28 дн. | §5.1 оценка для стабильной системы |

**CFD.** Для каждого рабочего дня `d` и этапа `s` считается `N_s(d)` — число задач, вошедших в `s` или дальше к дню `d`. Ширина полосы = `N_s − N_{s+1}`.

**Рабочие дни** — пн–пт. Праздники не учитываются (см. «Ограничения»).

## Что умеет вкладка 2 (`assets/state.js`)

- 6 KPI-плиток: **В системе**, **WIP**, **Бэклог**, **Узкое место** (с ростом очереди), **Баланс потока за 28 дн.**, **P85 Lead Time** (с числом «стареющих»).
- Блок **«Что видим → Что это значит → Что делать»** — формируется автоматически из тех же данных.
- **CFD** — накопительная диаграмма потока по этапам, с тултипом «сколько задач на каждом этапе» и суммой.
- **WIP по этапам** — «сейчас» vs «4 недели назад», отсортировано по текущему значению.
- **Поток по неделям** — «поступило / закрыто», баланс за 28 дней.
- **Возраст незавершённых задач** — гистограмма с порогом P85; рядом — таблица до 8 самых старых задач.
- **Переключатель периода** графиков: 4 нед. / 12 нед. / 26 нед. / весь.
- **Экспорт CFD в CSV** (разделитель `;`, UTF-8 с BOM — открывается в Excel без танцев с кодировкой).

Все настройки — из схемы. Нет `cfd.stages` — вкладка покажет, что дописать.

## Доступность и адаптивность

- Клавиатура: все кнопки, фильтры и переключатели работают без мыши. `skip-link` вверху.
- `aria-*`: живые регионы для статусов, `aria-sort` на колонках, `role="img"` + подпись на контейнерах графиков.
- Контраст: палитра проходит WCAG AA для текста и основных меток.
- Адаптив: 1 колонка < 860 px, графики пересчитывают размер при resize.
- `prefers-reduced-motion` уважается.
- Без ECharts (нет интернета): KPI, выводы, таблица и экспорт CFD работают; вместо графиков — сообщение.

## Ограничения

- Данные **не репрезентативны** и не отражают ни одну реальную организацию.
- Нет возвратов в предыдущие статусы (`rework`), отмен задач, праздничных дней.
- Лимиты парсера: CSV ≤ 20 МБ, схема ≤ 1 МБ, первые 200 ошибок показываются в отчёте.
- ECharts грузится с `cdn.jsdelivr.net` — для графиков нужен интернет.
- Дата среза зафиксирована в генераторе; для своих данных она вычисляется как максимум по колонкам этапов.
